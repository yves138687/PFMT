# Personal Knowledge System PRD（优化版）

## 1. 文档概述

### 1.1 产品名称
Personal Knowledge System

### 1.2 产品定位
构建一个融合 `Notion + Obsidian + Git + ChatGPT` 能力的个人知识系统，用于长期沉淀、组织、检索、编辑和备份个人知识资产。

### 1.3 本版优化目标
基于原始 PRD，重点做以下修正与增强：

- 将“私密空间”从“独立加密存储空间”调整为“隐藏机制”
- 将“仅备份链路加密”调整为“文件本体可选加密存储 + 备份链路可选二次加密”
- 补充隐藏文件展示、时效控制、搜索行为、AI 访问边界等关键规则
- 从产品经理视角补齐信息架构、核心流程、风控点和版本建议

### 1.4 术语定义

| 专有名词 | 定义 | 举例说明 |
| --- | --- | --- |
| 知识库 | 本系统管理的全部知识内容集合，包含文档、图片、视频、附件及其元数据。 | 用户上传了 `产品方案.md`、`需求评审.mp4`、`原型图.png`，它们共同组成知识库的一部分。 |
| 文件本体 | 文件的真实内容，不含展示层信息和业务元数据。 | 一段视频的二进制内容、一个 PDF 的实际文件内容。 |
| 文件元数据 | 用于管理和搜索的结构化信息，不等同于文件本体。 | 文件名、路径、标签、摘要、类型、大小、创建时间。 |
| 普通路径 | 默认可见、可参与元数据搜索的目录路径。 | `/工作/项目A/需求文档`。 |
| 私密路径 | 需要额外隐藏控制的目录路径，可配置为默认隐藏。 | `/个人/证件资料`、`/财务/合同扫描件`。 |
| 隐藏路径 | 被设置为默认不展示的目录路径。 | 用户将 `/个人/日记` 设为隐藏后，文件树默认不显示该目录。 |
| 隐藏文件 | 被设置为默认不展示的单个文件。 | `工资清单.xlsx` 所在目录可见，但该文件本身默认隐藏。 |
| 文件本体加密 | 对真实文件内容进行加密存储，避免存储层直接读取原文。 | 图片、视频、PDF 落盘前先加密，读取时再动态解密。 |
| 备份级加密 | 对导出的备份包再做一层可选加密，独立于主存储加密。 | 备份到 Git 前，将整个备份包再次加密后再上传。 |
| 存储对象名 | 文件在存储层使用的随机化名称，不等于原始文件名。 | 原文件名是 `合同.pdf`，存储对象名可能是 `8f2c1f0e-...bin`。 |
| 原始文件名 | 用户看到的真实文件名，仅保存在元数据或备份映射清单中。 | `项目复盘.docx`。 |
| 对象映射清单 | 用于恢复“存储对象名、原始文件名、file_id、路径”等关系的备份清单。 | 数据库丢失后，依靠清单恢复 `8f2c...bin` 对应的是 `简历.pdf`。 |
| file_id | 系统为每个文件分配的稳定唯一标识，用于密钥派生、映射和恢复。 | 同一个文件重命名后，`file_id` 不变。 |
| 流式加解密 | 在上传、下载、预览时按数据流分段加密或解密，避免整文件一次性进内存。 | 播放 2GB 视频时，系统按片段解密而不是一次性加载整个视频。 |
| 指定文件 | 用户明确选中并授权 AI 读取的单个文件或多个文件。 | 用户点击“发送给 AI”并选择 `会议纪要.md`。 |
| 当前打开文档 | 用户已进入阅读或编辑状态的文档，允许 AI 在该文档范围内读取必要上下文。 | 用户打开 `技术方案.md` 后，AI 可以基于该文档内容问答。 |
| 指定段落 | 用户在当前文档中显式选中的文本范围。 | 用户选中第三段并要求“请润色这段”。 |
| `@文件` 引用 | 用户在 AI 输入框中通过 `@` 显式附带文件，使 AI 仅基于这些文件工作。 | 输入 `@需求说明书.md 请总结核心需求`。 |
| AI 可读取范围 | 当前一次 AI 调用被允许读取的内容边界。 | 本次只允许读取“当前打开文档 + 选中段落”，不允许读取其他文件。 |

## 2. 要解决的问题

用户在长期积累个人知识时，通常会遇到以下问题：

- 知识分散在 Markdown、Word、PDF、附件、Git 仓库和云盘中，不易统一管理
- 知识可以保存，但难以形成结构化目录、标签和关联关系
- 有些内容希望“临时隐藏”而不是“真的删除”或“独立加密”
- AI 可以帮助整理内容，但用户对隐私边界、上下文暴露和备份安全存在顾虑
- 缺少稳定的导入、导出、备份和恢复能力，长期可迁移性不足

## 5. 核心概念设计

### 5.1 知识空间
系统中的知识内容统一纳入知识库管理，逻辑上可以按目录、标签和文档关系组织。

建议保留两类逻辑空间：

- 普通知识空间：默认空间，可搜索、可在用户指定范围内供 AI 处理、可参与知识关联
- 私密路径空间：用于承载需要额外隐藏控制的目录和文件

### 5.2 私密隐藏空间的定义
系统需要同时支持“普通路径”和“私密路径”的区分，但两类路径下的文件本体都应支持加密存储，隐藏能力作为附加选项存在。

用户可将以下对象标记为隐藏：

- 指定目录
- 指定文件

路径层面的建议定义：

- 普通路径：默认可见，可参与元数据搜索
- 私密路径：默认可以配置为隐藏，也可以仅作为逻辑分类存在

隐藏能力是可选项，被标记为隐藏后：

- 默认文件树不展示这些目录/文件
- 默认搜索结果不返回这些目录/文件
- 默认 AI 上下文不读取这些目录/文件

当用户主动开启“显示隐藏文件”后：

- 文件树必须返回所有被隐藏的目录/文件
- 搜索结果可按当前开关状态决定是否包含隐藏内容
- 系统应支持设置生效时长，例如 `10 分钟 / 30 分钟 / 本次会话`
- 支持提前关闭隐藏空间，即恢复完全展示所有数据

### 5.3 路径与加密的关系

- 路径分类解决的是“内容如何组织与默认如何展示”
- 加密解决的是“文件本体如何安全存储”
- 隐藏解决的是“某些路径或文件是否默认不展示”

三者不应混为一谈，推荐作为三套独立但可叠加的能力：

- 路径分类：普通路径 / 私密路径
- 文件保护：文件本体加密存储，可按系统配置开启
- 展示控制：隐藏路径 / 隐藏文件，可按目录或文件粒度开启

## 8. 私密隐藏机制详细规则

### 8.1 核心规则

1. 文件本体加密和隐藏展示是两套独立能力
2. 隐藏粒度至少支持“目录”和“文件”
3. 隐藏状态默认对文件树、搜索、AI 上下文生效
4. 用户可临时开启“显示隐藏文件”
5. 用户可配置隐藏展示的生效时间
6. 用户可关闭隐藏空间能力，恢复所有数据完全可见

### 8.2 推荐状态设计

- `隐藏关闭`：所有数据正常显示
- `隐藏开启`：隐藏内容默认不可见
- `临时展示隐藏内容`：在限定时间内展示隐藏内容，超时自动恢复

### 8.3 推荐交互

- 在目录或文件右键菜单中提供“设为隐藏”
- 在系统顶部或设置页提供“显示隐藏内容”开关
- 在开启展示隐藏内容时弹出明确提示，并要求选择时长
- 到期后自动恢复隐藏，并给出轻提示

### 8.4 边界规则

- 若父目录被隐藏，则其子目录和文件默认一并隐藏
- 若单文件被隐藏，但父目录未隐藏，则目录可见、文件隐藏
- 被隐藏文档的直链访问应校验当前隐藏状态
- 用户导出目录时，应明确提示是否包含隐藏内容

## 9. 搜索设计

### 9.1 普通状态

- 仅搜索非隐藏内容
- 搜索结果不暴露隐藏目录名、文件名、摘要

### 9.2 展示隐藏内容状态

- 搜索可包含隐藏内容
- 搜索结果中建议加“隐藏内容”标识

### 9.3 后续建议

- 支持标签搜索
- 支持高级筛选：目录、标签、时间、文件类型、是否隐藏
- 不支持 AI 全局主动检索文件内容
- AI 仅处理用户显式指定的文件或段落范围

## 10. 数据存储与备份设计

### 10.1 主存储原则
系统应支持对所有文件本体进行加密存储，该能力为系统级可选项。

本方案下需要区分三类数据：

- 文件本体：加密后的真实文件内容
- 文件元数据：文件名、路径、标签、摘要、类型、大小、时间等
- 访问控制数据：是否隐藏、所属路径类型、权限与日志等

其中：

- 文件本体支持加密存储
- 文件名不直接暴露在存储层
- 可搜索能力仅基于元数据、标签与摘要

### 10.2 存储分层设计

建议采用以下分层：

#### 10.2.1 路径层

- 普通路径
- 私密路径

路径用于逻辑组织和默认展示策略，不直接决定是否加密，因为加密是文件本体层的独立能力。

#### 10.2.2 文件本体层

- 所有文件本体以密文形式保存
- 加密后的存储对象名使用随机化命名
- 存储层不保留原始文件名作为对象名

#### 10.2.3 元数据层

- 原始文件名
- 原始路径
- 文件类型
- 标签
- 人工摘要或 AI 摘要
- 是否隐藏
- 所属路径类型

元数据进入数据库，用于搜索、展示和恢复。

### 10.3 文件名随机化与可回溯设计

为了避免文件本体在存储层暴露真实信息，建议：

- 加密后文件本体的对象名使用随机 ID 或 UUID
- 原始文件名仅保存在数据库元数据中
- 备份包中必须保留一份可恢复的清单文件，用于建立“随机对象名 ↔ 原始文件名 ↔ 元数据”的映射

建议不要直接用“随机后的文件名”作为唯一恢复依据，而应采用独立的清单机制。

### 10.4 文件密钥设计建议

这里最关键的问题不是“用原文件名还是随机文件名做密钥”，而是不要把文件名直接作为文件密钥的核心输入。

推荐做法：

- 系统持有主密钥
- 每个文件生成独立 `file_id`
- 基于 `file_id` 派生文件密钥，或直接生成独立文件密钥并加密保存
- 原文件名和随机对象名都只作为元数据或映射信息，不作为加密安全的核心依赖

原因：

- 原文件名可能重复、可猜测、可变更
- 随机对象名虽然更稳定，但数据库丢失时单靠对象名仍不足以恢复完整业务信息
- 以 `file_id + 密钥清单` 为中心，更利于备份恢复和密钥轮换

### 10.5 数据库丢失后的恢复要求

由于真实文件名只保留在元数据中，因此必须提前设计“脱离主数据库的恢复能力”。

建议每次备份都包含：

- 加密后的文件本体
- 元数据备份
- 对象映射清单
- 密钥封装信息
- 路径结构信息
- 标签和摘要信息

其中对象映射清单至少应能恢复：

- `file_id`
- 随机对象名
- 原始文件名
- 原始路径
- 文件大小
- 校验信息

这样即使数据库丢失，也可以通过备份包重建最小可用元数据索引。

### 10.6 流式加解密要求

由于系统需要支持大文件、图片、视频和附件，必须支持流式加解密。

要求包括：

- 上传时流式加密，避免一次性加载整个文件到内存
- 下载时流式解密，避免一次性加载整个文件到内存
- 视频和超大文件读取时支持分段读取或流式播放
- 若存在临时解密缓存，应限制时效并及时清理

### 10.7 备份原则
加密发生在“备份到第三方存储”的链路上，而不是主库存储阶段。

当系统执行备份时：

- 即使主存储已启用文件本体加密，备份包仍可选择是否再做一层备份级加密
- 若备份到第三方存储库，则支持加密后再上传
- 当前优先支持 `Git` 作为备份目标

### 10.8 推荐备份策略

- 文件本体以密文形式存储
- 数据库保存结构化元数据
- 备份导出时生成标准化备份包
- 备份包内包含映射清单与恢复所需元数据
- 若用户开启“备份加密”，则先加密备份包再推送到 Git 仓库
- 若用户关闭“备份加密”，则按普通方式推送备份包到 Git 仓库

### 10.9 建议备份内容

- 加密后的文件本体
- 目录结构
- 路径类型信息
- 标签关系
- 文件映射清单
- 文件元数据
- 配置项
- 隐藏规则配置
- 密钥封装信息

### 10.10 必须补充的能力

- 一键备份
- 定时备份
- 手动恢复
- 备份预览
- 备份日志
- 最近一次成功备份时间

## 11. 安全设计

### 11.1 当前建议的安全分层
原 PRD 中 `NORMAL / PRIVATE / SECRET` 的分层概念可以保留，但建议调整语义：

- `NORMAL`：普通文档，可搜索，可参与 AI
- `HIDDEN`：隐藏文档，默认不展示，不参与默认搜索和默认 AI 上下文
- `SENSITIVE`：高敏感文档，可追加二次确认或口令校验

### 11.2 更合理的安全策略

- 对文件本体提供系统级加密存储开关
- 对“访问路径”做限制，但不以此替代文件加密
- 对第三方备份提供可选加密
- 对高敏感操作增加确认和日志
- 对文件对象名做随机化处理，避免从存储层直接暴露业务信息

### 11.3 建议增加的保护能力

- 登录鉴权
- 二次确认
- 敏感内容访问日志
- 隐藏内容展示倒计时
- AI 读取隐藏内容前的显式授权

## 12. AI 能力设计

### 12.1 模型支持

- OpenAI 兼容接口
- DeepSeek
- 通义千问
- Ollama

### 12.2 AI 功能

- 指定文件总结
- 当前文档问答
- 段落级润色
- 段落级替换
- 段落级翻译
- 段落级续写
- 文档总结
- 自动标签生成

### 12.3 AI 能力分层

建议将 AI 能力明确分成两层：

#### A. 当前文档编辑助手
当用户已经打开某篇文档后，AI 可以在“当前打开文档”的范围内进行对话，并针对指定段落执行精细化编辑。

典型能力：

- 基于当前打开文档进行问答
- 润色
- 替换
- 翻译
- 续写
- 总结当前段落
- 基于上下文重写指定段落

#### B. 文件引用助手
用户可以像 Codex 一样通过 `@文件` 的方式显式引用某个文档，让 AI 读取并总结。

典型能力：

- `@某篇文档` 后让 AI 读取内容
- 总结单篇文档
- 对比两篇或多篇被 `@` 的文档
- 提取文档中的结论、待办、风险点

### 12.4 AI 访问边界

- AI 不具备全局主动检索知识库内容的能力
- AI 只允许读取用户显式指定的文件、选中的段落或 `@文件` 引用内容
- 当用户已打开某篇文档时，AI 允许在该文档范围内读取必要上下文用于对话
- 默认不读取隐藏内容
- 若用户开启“展示隐藏内容”，仍建议在 AI 使用隐藏内容前二次提示
- 发送给 AI 的上下文应明确可控，避免隐藏内容被误带出
- 即使当前文档上下文已授权，AI 也不得扩展读取其他未指定文件

### 12.5 AI 上下文建议

- 当前文档 ID
- 当前打开文档的必要上下文片段
- 选中文本
- 前后文
- 用户要求
- 是否允许使用隐藏内容
- 是否通过 `@文件` 显式引用
- 是否为用户手动选择的指定文件

### 12.6 AI 关键交互要求

#### 12.6.1 当前文档段落级处理

当用户已打开某篇文档并选中指定段落后，AI 应支持：

- 在当前文档范围内回答问题
- 润色该段
- 翻译该段
- 按要求替换该段
- 在该段后续写
- 给出多个改写候选

若用户未明确选中段落，但当前文档处于打开状态，AI 可在该文档上下文范围内对整篇文档进行受控问答与总结。

#### 12.6.2 指定文件处理

当用户明确选择一个文件后，AI 应仅基于该文件内容工作，不扩展到其他未指定文件。

支持能力：

- 总结该文件
- 按用户要求提取关键信息
- 基于该文件回答问题
- 生成或修改该文件对应摘要

#### 12.6.3 `@文件` 引用

当用户在输入框中通过 `@文件名` 或 `@路径` 引用文档时，系统应支持：

- 自动补全候选文件
- 将被引用文件加入 AI 上下文
- 让 AI 对被引用文件进行总结、问答或对比分析

## 14. AI 文档编辑交互

AI 文档交互建议拆成三种模式：指定文件阅读、当前文档编辑、`@文件` 引用阅读。

### 14.1 指定文件处理流程

1. 用户主动选择一个文件
2. 用户点击“发送给 AI”或通过文件菜单发起
3. 系统明确本次 AI 可读取的文件范围
4. 用户输入要求，例如“请总结这个文件”
5. AI 仅基于该文件返回结果

### 14.2 当前文档段落编辑流程

1. 选择文本
2. 点击 AI 处理
3. 选中文本进入 AI 输入区
4. 输入修改要求
5. AI 返回结果

若用户未选中文本，但当前文档处于打开状态：

1. 用户直接基于当前文档发起问题
2. 系统将当前打开文档作为本次 AI 可读取范围
3. AI 在该文档范围内读取必要上下文并返回回答
4. 不扩展读取其他未指定文件

### 14.3 当前文档结果操作

- 替换原文
- 插入到原文后方
- 复制结果
- 取消修改

### 14.4 `@文件` 引用流程

1. 用户在 AI 输入框中输入 `@`
2. 系统弹出文件候选列表
3. 用户选择一个或多个文件
4. 被引用文件进入 AI 上下文
5. 用户输入问题，例如“请总结这个文件”或“对比这两个文件的区别”
6. AI 基于引用文件返回总结或分析结果

## 19. 产品经理视角的优化建议

以下是从产品设计角度，当前构思还可以继续增强的重点。

### 19.1 不要只做“存”，要做“沉淀闭环”
当前 PRD 对“存储”和“编辑”描述较多，但对“知识沉淀闭环”还不够强。建议补充：

- 收集入口：快速新建、剪藏、上传附件、稍后整理
- 整理入口：待归档、待打标签、待总结
- 消费入口：最近访问、推荐阅读、相关文档

### 19.2 隐藏机制要有“防误触暴露”设计
隐藏内容最大的风险不是存储，而是误展示。建议补充：

- 开启展示隐藏内容时强提醒
- 展示状态明显可见
- 超时自动恢复
- AI 调用隐藏内容时再次确认

### 19.3 备份不只是“能备份”，还要“可恢复、可验证”
很多产品只做导出，不做恢复验证。建议至少补齐：

- 恢复演练入口
- 最近恢复记录
- 备份完整性校验
- 备份失败告警

### 19.4 搜索体验应成为核心竞争力
知识库产品真正的价值往往体现在“找得到”。建议优先强化：

- 标题搜索
- 标签搜索
- 标签筛选
- 最近修改
- 按文档类型筛选
- 隐藏内容过滤

### 19.5 AI 能力需要更可控，而不是更激进
建议把 AI 定位为“辅助编辑器”而不是“默认读取所有知识”。重点包括：

- 用户明确选择上下文
- 可查看实际发送给 AI 的内容
- 支持关闭 AI 对某些目录的访问
- 保留 AI 操作记录，便于追溯

### 19.6 增加版本与审计能力
个人知识库长期使用后，用户会非常需要：

- 文档历史版本
- 差异对比
- 删除恢复
- 敏感操作日志

### 19.7 建议增加“收件箱”概念
很多知识系统失败不是因为编辑器不够强，而是因为用户“不知道先放哪里”。建议增加：

- Inbox / 收件箱
- 稍后整理
- 一键归档到正式目录
