# Personal Knowledge System 项目阶段设计文档

## 1. 文档说明

### 1.1 目的

本文档用于基于当前已经明确的产品目标、隐私方案、技术方向和资源约束，重新整理项目推进阶段，明确：

- 第一阶段到底要做什么
- 每个阶段的边界在哪里
- 哪些功能先做闭环，哪些能力后续扩展
- 当前开发时应该优先保证什么、不应该提前做什么

### 1.2 当前规划基线

- 当前日期：`2026-07-24`
- 部署目标：单机、自托管、`2U2G` 低资源环境可运行
- 当前技术基线：`Vue 3 + TypeScript + FastAPI + SQLAlchemy + SQLite`
- 当前产品定位：单用户私密文件管理系统，逐步扩展为受控 AI 辅助的个人知识管理工具

### 1.3 规划原则

- 优先做最小可用闭环，不追求一开始功能大而全
- 优先把登录、配置、文件上传、加密、文件树跑通
- AI 能力延后接入，且始终保持“用户指定范围”边界
- 优先保证隐私与可控性，再逐步补体验和高级能力
- 前端第一阶段可以保留占位页面，但骨架和交互主路径要先成型

---

## 2. 长远目标与当前切入点

### 2.1 长远目标

项目长远上希望做到：

- 可靠管理多类型私密文件
- 支持普通路径与私密路径区分
- 支持文件本体加密存储与可恢复备份
- 支持基于元数据、标签、摘要的可搜索管理
- 支持在文件级、段落级、当前文档级范围内调用 AI
- 支持文档预览、编辑、多媒体播放等更完整的使用体验

### 2.2 当前切入点

基于你刚刚拆分的第一阶段内容，当前项目不再从“完整知识库能力”切入，而是先从下面这条主链路切入：

1. 用户登录
2. 系统配置
3. 文件上传
4. 文件流式加密存储
5. 文件树展示
6. 前端基础布局

这条链路的意义是：

- 先把“可登录、可配置、可上传、可安全保存、可看到结构”做成
- 暂时不被 AI、富文本、多媒体预览这些后续能力拖慢节奏
- 为后续一切扩展打稳基础

---

## 3. 项目阶段总览

建议项目按 4 个阶段推进：

1. 第一阶段：基础可用闭环
2. 第二阶段：基础文件管理增强
3. 第三阶段：文件内 AI 能力接入
4. 第四阶段：预览、编辑、备份与产品完善

阶段总览如下：

| 阶段 | 目标 | 核心能力 | 优先级 |
| --- | --- | --- | --- |
| 第一阶段 | 做出最小可用闭环 | 登录、系统配置、上传、流式加密、文件树、基础布局、Markdown 查看 | P0 |
| 第二阶段 | 完善文件管理能力 | 文件列表、路径管理、隐藏功能、基础预览、标签、搜索 | P1 |
| 第三阶段 | 接入受控 AI | 当前文档对话、指定文件总结、段落级润色改写 | P1 |
| 第四阶段 | 补齐产品完成度 | 富文本、PDF、视频、备份恢复、审计增强 | P2 |

---

## 4. 第一阶段：基础可用闭环

### 4.1 阶段目标

第一阶段的唯一目标，是交付一个真正可以运行的最小版本，让用户完成下面这条主流程：

1. 打开系统
2. 登录
3. 配置基础系统开关
4. 上传文件
5. 文件在服务端进行流式加密存储
6. 在前端看到基础目录树和布局

这个阶段不追求“好看、完整、功能多”，只追求：

- 主链路打通
- 数据结构稳定
- 目录结构稳定
- 加密与上传链路可验证

### 4.2 第一阶段范围

你当前拆分的第一阶段功能，结合最小可用体验补充后，正式收敛为以下 6 个模块：

1. 用户登录
2. 基础系统配置
3. 文件上传并流式加密
4. 基础文件树构建
5. 前端登录页与基础页面布局
6. 最基础的 Markdown 文档查看

### 4.3 第一阶段功能设计

#### 4.3.1 用户登录

目标：

- 支持单用户登录
- 登录后才能访问业务页面
- 为后续系统配置、文件上传、文件树接口提供登录态基础

本阶段要实现：

- 登录页
- 账号密码校验
- 登录成功后签发会话或令牌
- 登录态校验中间件
- 退出登录

本阶段先不做：

- 多用户
- 复杂权限
- 二次验证
- 密码找回

#### 4.3.2 基础系统配置

目标：

- 先把影响系统主行为的几个关键开关做出来
- 为后续文件管理与加密能力提供统一控制入口

本阶段建议至少支持以下配置项：

- 是否开启文件隐藏功能
- 是否开启文件本体加密功能
- 是否默认展示隐藏内容
- 本地存储根路径

如果你希望再稍微往后兼容一点，也可以预留：

- 是否开启 AI 功能
- 是否启用备份功能

但这两个在第一阶段可以只保留数据库字段和后端配置结构，不强制做完整 UI。

#### 4.3.3 文件上传并进行流式加密

目标：

- 支持文件上传到服务端
- 文件在写入存储层时完成流式加密
- 避免大文件一次性读入内存

本阶段要实现：

- 文件上传接口
- 文件元数据入库
- 随机化存储对象名
- 流式加密写入磁盘
- 上传完成后返回文件基础信息

本阶段重点约束：

- 加密写入和元数据入库必须形成清晰的成功 / 失败处理逻辑
- 文件原始名称不能直接作为存储层真实文件名
- 后端必须预留后续解密读取能力的接口设计空间

本阶段先不强求：

- 分片上传
- 秒传
- 断点续传
- 大文件高级传输优化

#### 4.3.4 基础文件树构建

目标：

- 先把目录结构表达出来
- 为后续文件列表、路径管理、隐藏控制打基础

本阶段要实现：

- 根节点展示
- 基础目录树查询接口
- 基础目录创建
- 路径与文件关联关系建立

本阶段建议：

- 第一阶段先支持最基础目录树，不急着做拖拽、移动、重命名
- 私密路径概念可以先落在字段和结构上，复杂交互放第二阶段

#### 4.3.5 前端登录页与基础页面布局

目标：

- 先把前端最核心的页面骨架搭出来
- 未开发完成的业务区允许用占位内容承接

本阶段要实现：

- 登录页
- 登录后主布局
- 顶部导航栏
- 左侧目录树区域
- 右侧主内容区域
- 系统配置页基础入口
- 文件上传入口

可接受的占位方式：

- 文件列表区域先展示占位表格或占位空状态
- 文件详情区域先展示“待后续实现”
- AI、预览、多媒体区域可以先不开放，只保留菜单或空模块

#### 4.3.6 最基础的 Markdown 文档查看

目标：

- 让第一阶段上传后的文档类文件至少有一种可以立即查看内容
- 优先把 `Markdown` 作为第一种完整打通的文本型文件

本阶段要实现：

- `Markdown` 文件基础读取接口
- `Markdown` 文件查看页或查看面板
- 文本内容安全渲染
- 至少支持 `.md` 文件打开查看

本阶段约束：

- 当前先做“查看”，不做编辑
- 当前先支持基础渲染，不追求完整富文本能力
- 图片内嵌、目录导航、代码高亮等增强体验可放后续阶段

### 4.4 第一阶段不纳入范围

以下能力明确不放在第一阶段，避免范围失控：

- 全局搜索
- 标签管理
- 文件隐藏操作细节
- 文件列表复杂筛选
- 文本编辑
- PDF 预览
- 图片查看优化
- 视频播放
- AI 总结 / 润色 / 对话
- Git 备份
- 恢复流程

### 4.5 第一阶段交付结果

第一阶段结束后，应至少拿到以下交付物：

- 后端可启动
- 前端可启动
- 数据库可初始化
- 登录流程可用
- 系统配置可读写
- 文件上传可用
- 文件本体可流式加密写入
- 文件树可展示
- 基础页面布局可使用
- `Markdown` 文档可基础查看

### 4.6 第一阶段完成标准

满足以下条件，才算第一阶段完成：

1. 未登录用户无法访问业务页面
2. 用户可成功登录并退出
3. 系统配置可修改并持久化
4. 上传文件后数据库记录正确
5. 上传后的存储对象名为随机值，不直接暴露原始文件名
6. 文件写入过程采用流式处理，不依赖整文件一次性加载到内存
7. 前端登录后可进入主布局并看到基础文件树区域
8. 至少支持已上传 `.md` 文件的基础查看

### 4.7 第一阶段的技术落点

后端重点：

- `FastAPI` 登录接口
- 配置读写接口
- 文件上传接口
- 文件树查询接口
- 流式加密存储服务

前端重点：

- 登录页
- 基础 Layout
- 顶部导航
- 左侧树
- 右侧业务容器
- 配置页基础表单
- 上传入口
- Markdown 查看页 / 查看面板

数据库重点：

- `user_account`
- `user_session`
- `system_setting`
- `file_path`
- `file_info`
- `audit_log`

## 5. 第二阶段：基础文件管理增强

### 5.1 阶段目标

在第一阶段闭环跑通后，第二阶段开始把“能用”提升到“像一个真正的文件管理系统”。

### 5.2 主要能力

- 文件列表页
- 文件详情页
- 目录重命名
- 路径移动
- 文件重命名
- 文件隐藏
- 路径隐藏
- 显示隐藏内容开关
- 标签管理
- 元数据搜索
- 基础文本 / 图片 / PDF 文件展示

### 5.3 阶段意义

- 让用户不仅能上传，还能真正管理
- 把隐藏机制和元数据搜索补齐
- 为后续 AI 读取指定文件范围提供前提

---

## 6. 第三阶段：文件内 AI 能力接入

### 6.1 阶段目标

在文件管理能力稳定后，再接入受控 AI，始终保持“用户明确指定范围”的原则。

### 6.2 主要能力

- 指定文件总结
- 当前打开文档上下文对话
- 指定段落润色
- 指定段落改写
- 指定段落翻译
- 指定段落续写 / 扩写
- AI 可读取范围提示
- AI 调用记录

### 6.3 阶段边界

- 不做 AI 全局检索
- 不做后台自动扫描
- 不做未授权文件自动入上下文

---

## 7. 第四阶段：预览、编辑、备份与产品完善

### 7.1 阶段目标

补足日常使用体验和可恢复能力，让系统从“基础可用”走向“长期可用”。

### 7.2 主要能力

- Markdown 编辑
- 富文本编辑
- PDF 在线预览
- 图片预览优化
- 视频 / 音频播放
- 备份到 Git
- 备份级加密
- 恢复能力
- 审计增强
- 最近访问
- 收藏

---

## 8. 阶段推进建议

### 8.1 当前最合理的推进顺序

建议按以下顺序推进：

1. 先做第一阶段，不扩需求
2. 第一阶段跑通后，再进入第二阶段
3. 第二阶段完成文件管理基础能力后，再接第三阶段 AI
4. 最后再做第四阶段体验增强与备份恢复

### 8.2 为什么这样分

这样分的好处是：

- 风险最低
- 范围最清晰
- 更适合单人或小团队推进
- 更符合 `2U2G` 资源限制
- 能尽快验证最关键的加密存储链路

### 8.3 当前开发时的执行原则

现阶段开发时，建议始终记住这几条：

1. 第一阶段只做主链路，不做功能蔓延
2. 先保证后端链路正确，再补前端体验
3. 先把文件加密、元数据入库、目录树跑通，再谈搜索和 AI
4. 所有后续能力都要建立在“用户明确授权范围”之上

## 9. 当前建议结论

结合你这次对第一阶段的拆分，当前项目最合适的阶段设计是：

### 第一阶段

- 登录
- 基础系统配置
- 文件上传
- 流式加密存储
- 基础文件树
- 前端登录页与基础布局

### 第二阶段

- 文件列表
- 路径 / 文件隐藏
- 标签
- 元数据搜索
- 基础预览
- 统一文档打开、保存与 `.txt` / `.md` / `.html` 转换

### 第三阶段

- 文件内 AI 总结、润色、改写、翻译、续写
- 当前文档上下文对话

### 第四阶段

- 更完整的富文本能力
- PDF / 视频 / 音频
- 备份恢复
- 审计与产品完善

如果按这个节奏推进，项目会更稳，也更容易在前期快速拿到一个真正可演示、可验证、可继续开发的版本。
